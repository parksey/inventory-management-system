# 협업 워크플로우

이 레포에서 일이 **어떤 문서로 정의되고, 어떤 순서로 흘러가고, 누가 무엇을 결정하는지**를 정의한다.
1인 프로젝트지만 PM과 개발자의 역할을 나눠 협업 흐름을 그대로 따르고, AI(Claude Code)가 두 역할의 실행을 돕는다.

---

## 1. 큰 그림

```
기능 요구사항 ── 구체화 ──▶ Issue  Issue  Issue …
   (PM)        (PM + AI)      │
                              ▼  이슈마다 AI 세션 1개
                         기능 명세서 ── 승인 ──▶ PR  PR  PR …
                          (개발 전)              (각각 테스트 코드 + 테스트 케이스)
```

| 문서 | 답하는 질문 | 언제 | 어디에 |
|---|---|---|---|
| **기능 요구사항** | 사용자가 무엇을 할 수 있어야 하는가 | 기능 요청이 들어왔을 때 | 상위 이슈 (`requirement` 라벨) |
| **Issue** | **무엇을** 할 것인가 — 개발할 기능 / 수정할 기능 / 고칠 버그 | 요구사항을 구체화한 결과 | 요구사항 이슈의 sub-issue |
| **기능 명세서** | **어떻게 개발할** 것인가 | 개발 들어가기 전 | `docs/specs/{이슈번호}-{영문-설명}.md` (승인은 이슈 코멘트) |
| **PR** | **어떻게 개발했는가** | 개발한 뒤 | Pull Request |

각 문서는 자기 질문에만 답한다. 이슈에 설계를 쓰지 않고, 명세서에 구현 결과를 쓰지 않는다. 역할이 분명해야 나중에 "무엇을 하려 했고(이슈) → 어떻게 하기로 했고(명세서) → 실제로 어떻게 했는지(PR)"를 거슬러 올라갈 수 있다.

---

## 2. 역할

| 역할 | 하는 일 | 결정하는 것 |
|---|---|---|
| **PM** (사용자) | 기능 요구사항 정의, 구체화, 이슈 등록 | 요구사항 범위, 이슈 분할, 우선순위 |
| **개발자** (사용자) | 이슈별 세션 진행 | 기능 명세서 승인, 설계 선택, 머지 |
| **AI** (Claude Code) | 두 역할의 실행 — 구체화 질문, 이슈 초안, 명세서, 구현, 테스트, PR, 셀프 리뷰 | 결정하지 않는다. 결정이 필요한 지점을 드러낸다 |

PM과 개발자는 같은 사람이지만 승인은 단계마다 따로 남긴다: **이슈 등록**(PM) / **명세서 승인**(개발자) / **머지**(개발자).

---

## 3. 단계

### 3.1 요구사항 → 구체화 → Issue (PM)

1. **요구사항 등록** — 기능 요청을 사용자 관점으로 정리해 `requirement` 이슈로 올린다.
2. **구체화** — AI가 요구사항의 빈칸(입력 범위, 예외 상황, 범위 밖 항목, 다른 기능과의 관계)을 질문으로 드러내고, PM이 답한다.
3. **이슈 도출** — 구체화 결과로 나온 "해야 할 일"을 이슈로 나눈다. 이슈 하나는 아래 중 하나다.

| 유형 | 의미 | 라벨 |
|---|---|---|
| 기능 개발 | 없던 기능을 만든다 | `feat` |
| 기능 수정 | 있는 기능의 동작을 바꾼다 | `change` |
| 버그 수정 | 의도와 다르게 동작하는 것을 고친다 | `fix` |
| 작업 | 기능 외 작업 — 빌드 · CI · 배포 · 문서 | `chore` `ci` `deploy` `docs` |

4. **등록** — PM이 이슈 목록을 승인하면 요구사항 이슈의 sub-issue로 등록한다.

**이슈 크기** — AI 세션 하나로 끝낼 수 있어야 한다. 아래 중 하나라도 해당하면 나눈다.
- 완료 조건이 7개를 넘는다
- 서로 무관한 목표가 섞여 있다 (예: "Helm chart + 이미지 배포 자동화")
- 아직 정하지 않은 결정이 포함돼 있다 → 결정된 부분만 이슈로

### 3.2 Issue → 기능 명세서 (개발자, 개발 전)

**이슈 하나 = AI 세션 하나.** 세션은 다른 이슈를 넘나들지 않는다.
- 세션이 시작할 때 필요한 정보(이슈, 명세서, 규칙)가 정해져 있어 이전 대화에 기대지 않는다.
- 세션 하나로 끝나지 않으면 이슈가 너무 크다는 신호가 된다.
- 이슈마다 브랜치 · worktree가 따로라 여러 세션을 병렬로 돌려도 간섭하지 않는다.

세션은 먼저 기능 명세서를 `docs/specs/`에 파일로 작성하고, **개발자가 승인해야 개발을 시작한다.**
- 명세서는 첫 PR의 브랜치에 커밋해 push하고, 이슈에 명세서 링크와 요약 코멘트를 남긴다.
- 승인은 그 코멘트에 👍 반응이나 이슈에 "승인" 코멘트로 남긴다.
- 별도의 명세서 PR은 만들지 않는다. 명세서는 첫 PR과 함께 main에 들어간다.

### 3.3 기능 명세서 → PR (개발자, 개발 후)

명세서의 **PR 계획**대로 개발한다. 한 이슈에서 PR이 여러 개 나올 수 있다.

```
PR 1 ─ 셀프 검증 ─ 리뷰 ─ 머지   Refs #N
PR 2 ─ 셀프 검증 ─ 리뷰 ─ 머지   Refs #N
PR 3 ─ 셀프 검증 ─ 리뷰 ─ 머지   Closes #N   ← 마지막 PR이 이슈를 닫는다
```

- 각 PR은 단독으로 머지 가능해야 한다 (빌드 · 테스트 통과, 기능이 반쯤 노출되지 않음).
- **각 PR은 자기 범위의 테스트 코드와 테스트 케이스를 포함한다** ([§5](#5-테스트-규칙)).
- 머지는 개발자가 지시할 때만 한다.

### 3.4 기록

- 리뷰어가 알아야 할 설계 결정은 `docs/adr/`에 ADR로 남긴다.
- 개발 중 발견한 범위 밖 작업은 코드에 TODO로 남기지 않고, PM에게 새 이슈로 제안한다.

## 4. 문서별 양식

### 기능 요구사항 — `requirement` 이슈
| 섹션 | 내용 |
|---|---|
| 배경 | 왜 필요한가 |
| 요구사항 | "~할 수 있어야 한다" — 사용자 관점 |
| 성공 기준 | 요구사항이 충족됐다고 판단하는 기준 |
| 제약 · 범위 밖 | 지켜야 할 조건, 이번에 하지 않는 것 |

구체화로 나온 이슈는 sub-issue로 연결되어 요구사항 이슈에서 진행 상황이 보인다.

### Issue — 무엇을
설계나 구현 방법은 쓰지 않는다. 그건 기능 명세서의 일이다.

| 유형 | 섹션 |
|---|---|
| 기능 개발 | 배경 · 목적 / 요구사항 / 완료 조건 / 범위 밖 / Open Questions |
| 기능 수정 | 현재 동작 / 바꿀 동작 / 이유 / 완료 조건 / 영향 범위 |
| 버그 수정 | 현상 / 재현 방법 / 기대 동작 / 완료 조건 |
| 작업 | 배경 · 목적 / 작업 내용 / 완료 조건 |

- 완료 조건은 동작으로 검증할 수 있게 쓴다 ("재고보다 많이 출고하면 거절된다").
- 불명확한 부분은 추측해서 채우지 않고 Open Questions에 남긴다.

### 기능 명세서 — 어떻게 개발할지 (`docs/specs/{이슈번호}-{영문-설명}.md`)
```markdown
# 기능 명세 — 재고 출고 (#7)

### 요구사항 해석
- 이슈의 요구사항과 완료 조건을 개발 관점으로 풀어쓴 것

### 설계
- 인터페이스: API(메서드 · 경로 · 요청/응답 · 상태 코드), 주요 클래스 · 메서드
- 데이터: 테이블 · 컬럼 · 제약 변경 (해당 시)
- 흐름: 처리 순서, 트랜잭션 · 락 범위 (해당 시)

### 비즈니스 규칙
- R1. 출고 수량은 현재 재고를 초과할 수 없다

### 예외 케이스
| 상황 | 결과 |
|---|---|

### 테스트 케이스
| ID | 대상 규칙 | Given | When | Then | 종류 |
|---|---|---|---|---|---|
| TC-7-01 | R1 | 재고 10 | 11 출고 | 409 INSUFFICIENT_STOCK, 재고 10 유지 | 통합 |

### PR 계획
| PR | 범위 | 포함 테스트 케이스 |
|---|---|---|
| 1 | 출고 도메인 로직 | TC-7-01 ~ TC-7-03 |
| 2 | 출고 API | TC-7-04 ~ TC-7-06 |

### 결정 필요

### 변경 이력
```

- 테스트 케이스 ID는 `TC-{이슈번호}-{두 자리 순번}`. 규칙마다 최소 1개, 정상 · 경계값 · 예외를 각각 다룬다.
- 코드 변경이 없는 작업 이슈(문서 · CI · 배포 설정)는 테스트 케이스 대신 **검증 방법**(실행 명령과 기대 결과)을 쓴다.
- 테스트로 만들 수 있는 확인(예: `curl`로 health 확인 → HTTP 통합 테스트)은 검증 방법이 아니라 테스트 케이스로 쓴다. 검증 방법은 자동화하기 어려운 것만 남긴다.
- 프레임워크 기본 동작(Boot 기본 설정값, `enabled=false`면 빈이 안 생김 등)은 테스트하지 않는다. 우리가 정한 설정과 코드만 검증한다.
- 파일명 예: `docs/specs/7-outbound.md`. 이슈 하나에 명세서 하나.
- 개발 중 명세가 바뀌면 그 PR에서 명세서 파일을 함께 고치고, "변경 이력"에 사유를 한 줄 남긴다. PR의 "명세와 달라진 점"에도 쓴다.

### PR — 어떻게 개발했는지
`.github/pull_request_template.md`를 따른다.

| 섹션 | 내용 |
|---|---|
| 관련 이슈 | `Closes #N` 또는 `Refs #N` |
| 구현 내용 | 무엇을 했는가 — 커밋별이 아니라 한 일 단위 항목으로 (예: "p6spy 모듈화 및 프로파일 분리") |
| 명세와 달라진 점 | 무엇이 왜 달라졌는가 (없으면 "없음") |
| 설계 결정 · 트레이드오프 | 실제로 비교한 대안과 선택 이유 (없으면 "없음") |
| 테스트 케이스 | 이 PR이 다룬 TC의 시나리오 · 테스트 위치 · 결과 **(필수)** |

## 5. 테스트 규칙

**코드(`src/main`)를 바꾸는 PR은 테스트를 반드시 포함한다.**

| 규칙 | 강제 방법 |
|---|---|
| `src/main` 변경이 있는 PR은 `src/test` 변경도 있어야 한다 | CI `test-required` 검사 — 위반 시 머지 불가 |
| PR 본문에 적은 테스트 케이스가 테스트 코드에 실제로 있다 | 셀프 검증 스크립트 |
| 이슈를 닫는 마지막 PR에서는 명세서의 테스트 케이스가 모두 코드로 존재한다 | 셀프 검증 스크립트 |
| 테스트 이름에 테스트 케이스 ID를 붙인다 | `@DisplayName("TC-7-01 ...")` |

명세서 · 테스트 코드 · PR이 같은 테스트 케이스 ID로 이어진다.
```
기능 명세서 TC-7-01  →  @DisplayName("TC-7-01 …")  →  PR 테스트 케이스 표
```

## 6. 예외 흐름

| 상황 | 처리 |
|---|---|
| 개발 중 범위가 커진다 | 현재 이슈 범위만 마무리하고, 나머지는 PM에게 새 이슈로 제안한다 |
| 설계 결정이 필요한데 미정이다 | 진행을 멈추고 선택지를 이슈 코멘트로 제시한다. 필요하면 `blocked` 라벨 |
| 머지된 코드에서 버그 발견 | 버그 수정 이슈를 새로 만든다. 닫힌 이슈를 다시 열지 않는다 |
| 코드에 TODO를 남기고 싶다 | TODO 대신 이슈를 제안한다 |
| 세션이 이슈를 끝내지 못하고 길어진다 | 이슈가 너무 컸다는 신호. 머지된 PR까지로 이슈 범위를 줄이고, 남은 부분을 새 이슈로 나눈다 |
| CI 실패 | 원인을 고친 커밋을 추가한다. 테스트를 비활성화해서 통과시키지 않는다 |
| 테스트를 쓸 수 없는 코드 변경 | 기동 테스트 등 최소 검증을 작성한다. 정말 불가능하면 PR에 사유를 쓰고 개발자가 판단한다 |
