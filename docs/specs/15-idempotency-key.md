# 기능 명세 — 중복 요청 한 번만 반영 (멱등성 키) (#15)

### 요구사항 해석
- 입고, 출고 요청은 `Idempotency-Key` 헤더로 클라이언트가 만든 키를 함께 보낸다. 사용자 행동 하나에 키 하나다. 키가 없으면 400이다.
- 같은 키로 다시 오면 재고를 다시 바꾸지 않고 처음과 같은 응답(200, `data` = `null`)을 돌려준다. 입고, 출고는 원래 응답에 데이터를 담지 않아서(#12) 처음 응답을 따로 저장하지 않아도 같은 응답을 만들 수 있다.
- 같은 키인데 요청 내용(입고/출고 구분, 상품 코드, 수량, 요청자)이 다르면 422로 거절한다.
- 여러 Pod에 같은 키 요청이 동시에 와도 하나만 반영된다. 앱 메모리가 아니라 DB 유니크 제약으로 보장한다.
- **성공한 요청만 키를 남긴다.** 실패한 요청(재고 부족 409 등)은 트랜잭션이 롤백되면서 키도 남지 않아, 같은 키로 다시 보내면 다시 처리한다 (아래 "실패한 요청의 키" 참고).
- 키는 지우지 않고 영구 보관한다 (아래 "보관 기간" 참고).
- 키는 요청자별로 나누지 않고 전역에서 유일하다. 요청자 ID(`X-User-Id`)는 인증된 값이 아니라 요청자별로 나눠도 보안상 얻는 것이 없고, 전역이어야 "같은 키, 다른 요청자"가 422로 드러난다. 요청자별로 나누면 같은 행동이 요청자 값만 다르게 두 번 반영될 수 있다.
- 키가 다른 중복 요청은 걸러내지 않는다 (이슈의 범위 밖. 키를 다시 쓰는 것이 클라이언트의 계약이다).

**용어**

| 용어 | 뜻 |
|---|---|
| 멱등성 키 (`IdempotencyKey`) | 클라이언트가 사용자 행동 하나마다 만드는 문자열. 같은 행동을 다시 보낼 때(재시도, 더블 클릭) 같은 키를 쓴다. UUID를 권장하지만 형식은 강제하지 않는다 |
| 멱등성 기록 (`IdempotencyRecord`) | 처리한 키와 그 요청 내용. 재전송인지, 키를 잘못 재사용한 것인지 가리는 데 쓴다 |

### 설계

**데이터** — 멱등성 기록 테이블을 추가한다 (`inventory/schema`의 `V15_1__create_idempotency_record.sql`)

```sql
CREATE TABLE idempotency_record (
    idempotency_key  VARCHAR(64) PRIMARY KEY,
    type             VARCHAR(20) NOT NULL,
    product_code     VARCHAR(64) NOT NULL,
    quantity         BIGINT      NOT NULL,
    requester_id     VARCHAR(64) NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT ck_idempotency_record_type CHECK (type IN ('INBOUND', 'OUTBOUND'))
);
```
- 키가 PK라 같은 키는 한 행만 들어간다. 동시성 보장이 이 제약 하나에 걸려 있다.
- 요청 내용을 해시 하나가 아니라 컬럼 네 개로 둔다. 비교할 값이 넷뿐이고, 해시로 두면 거절할 때 무엇이 달랐는지 알 수 없다.
- `product_id`가 아니라 `product_code`를 둔다. 미등록 상품의 첫 입고는 키를 넣는 시점에 상품이 아직 없다.
- `created_at`은 지금 쓰지 않는다. 나중에 정리나 파티션을 붙일 때의 기준이다. 시각은 Pod 시계가 아니라 DB `now()`로 넣어 Pod끼리 시계가 어긋나도 같은 기준이 된다.
- #12 명세에서는 원장에 키 컬럼을 두기로 했었는데, 별도 테이블로 바꿨다. 이유는 아래 "왜 별도 테이블인가".

**도메인** (`inventory/core`)

| 패키지 | 클래스 | 역할 |
|---|---|---|
| `idempotency.entity` | `IdempotencyKey` (record) | 공백이거나 64자를 넘으면 `INVALID_IDEMPOTENCY_KEY`. 엔티티에서는 PK 컬럼(문자열)으로 두고 getter가 VO로 돌려준다 |
| `idempotency.entity` | `IdempotencyRecord` | `of(key, type, productCode, quantity, requesterId)`. `verifySameRequest(IdempotencyRecord)`: 내용이 다르면 `IDEMPOTENCY_KEY_REUSED`, 메시지에 다른 항목 이름(`quantity` 등)을 담는다 |
| `idempotency.port` | `IdempotencyStore` | `saveOrGetProcessed(IdempotencyRecord)` → `Optional<IdempotencyRecord>`. 처음 보는 키면 저장하고 빈 값, 이미 성공한 키면 그 기록 |
| `inventory` | `InventoryService.inbound(IdempotencyKey, InboundCommand)`, `outbound(IdempotencyKey, OutboundCommand)` | 키를 Command와 별도 파라미터로 받아 맨 앞에서 확인한다 (아래 흐름) |

`ErrorCode` 추가: `INVALID_IDEMPOTENCY_KEY`(INVALID), `IDEMPOTENCY_KEY_REUSED`(UNPROCESSABLE).

**키를 Command에 넣지 않고 별도 파라미터로 받는 이유**
- Command의 필드(상품 코드, 수량, 요청자)는 "무엇을 할지"다. 재고 변경에 쓰이고 원장에 남는다. 요청자도 "누가 했는지"라는 업무 기록이라 원장에 남는다.
- 멱등성 키는 "이 요청이 몇 번째 시도인지"를 가리는 전달 계층의 꼬리표다. 재고 변경에 쓰이지 않고 원장에도 남지 않는다.
- 성격이 다른 값을 시그니처에서 나눠 보이게 한 것이다. Command는 "무엇을 할지"만 담는다.
- 대안: 키 확인을 감싸는 빈(`IdempotentInventoryService`)으로 빼서 `InventoryService`가 키를 전혀 모르게 하는 방법. 클래스가 하나 늘고 트랜잭션이 바깥 빈에서 시작해 안으로 이어지는 흐름을 따라가야 해서, 멱등성을 붙일 API가 둘뿐인 지금은 과하다. 세 개 이상으로 늘어나면 다시 검토한다.

- 422 메시지에는 다른 항목의 **이름만** 담고 저장된 값은 담지 않는다. 키가 우연히 겹친 다른 요청자에게 앞 요청의 상품, 수량, 요청자가 보이지 않게 하기 위해서다.

**저장** (`inventory/db`의 `db.idempotency`)
- `IdempotencyRecordJpaRepository.insertIfAbsent(...)`: `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING`, 넣은 행 수를 돌려준다. `ProductJpaRepository.insertIfAbsent`와 같은 모양이다.
- `IdempotencyStoreAdapter`가 행 수를 `boolean`으로 바꾼다.

**API** (`app`)

입고, 출고 모두 `Idempotency-Key` 헤더를 받는다 (`ApiHeaders.IDEMPOTENCY_KEY`). 경로와 본문은 그대로다.
```http
POST /api/v1/inventory/TS-BASIC-BLK-M/outbound
X-User-Id: worker-01
Idempotency-Key: 6f1c2a3e-9b7d-4c1a-8e2f-0a5b3c7d9e11
Content-Type: application/json

{"quantity": 3}
```

| 상황 | 상태 | `code` |
|---|---|---|
| 처음 보는 키 | 기존과 같음 (성공 200, 재고 부족 409 등) | |
| 이미 성공한 키, 같은 내용 | 200 | `SUCCESS`, `data` = `null`, 재고 그대로 |
| 이미 성공한 키, 다른 내용 | 422 | `IDEMPOTENCY_KEY_REUSED` |
| `Idempotency-Key` 없음 | 400 | `BAD_REQUEST` |
| `Idempotency-Key` 공백, 65자 이상 | 400 | `INVALID_IDEMPOTENCY_KEY` |
| 같은 키 요청이 처리 중이고 3초 넘게 끝나지 않음 | 503 | `SERVICE_UNAVAILABLE` + `Retry-After: 1` |

- 헤더 이름 `Idempotency-Key`는 IETF 초안(httpapi-idempotency-key-header)의 이름이다. 요청자 ID와 같은 이유로 본문이 아니라 헤더로 받는다. 요청 내용이 아니라 요청에 대한 정보다.
- 내용이 다를 때 422인 이유: 같은 IETF 초안이 키 재사용에 422를 쓴다. 요청 형식(400)은 맞고, 재고 상태와 충돌(409)한 것도 아니며, 이 키로는 처리할 수 없는 요청이다.
- **IETF 초안과 다른 점**: 초안은 같은 키가 아직 처리 중이면 즉시 409를 권한다. 이 명세는 앞 요청이 끝날 때까지 최대 3초 기다렸다가 200(앞 요청 성공) 또는 처음부터 처리(앞 요청 실패)한다. 클라이언트는 재시도 한 번으로 최종 결과를 받고, 중복 반영 방지라는 초안의 목적에도 어긋나지 않는다. 3초를 넘으면 503이다.
- 키 길이 상한은 64자다. UUID(36자)에 충분하고, 요청자 ID, 상품 코드와 같은 상한이다.

**클라이언트 재시도 계약** (API 문서에 함께 적는다)
- 같은 키로 자동 재시도해도 되는 경우: 응답을 못 받음(네트워크 오류, 타임아웃), 5xx, 503.
- 409, 404, 422, 400은 최종 응답이다. 다시 하려면 사용자가 새로 행동해야 하고, 그때는 새 키를 쓴다.
- 이유: 실패한 요청은 키를 남기지 않아서(R4) 같은 키로 다시 보내면 다시 처리된다. 예를 들어 409(재고 부족)를 받은 출고를 오프라인 큐에 넣었다가 몇 시간 뒤 같은 키로 자동 재전송하면, 그 사이 입고가 있었을 때 사용자가 이미 포기한 출고가 뒤늦게 반영된다.

**흐름** — `InventoryService.inbound`, `outbound`, 각각 `@Transactional` 하나

```java
@Transactional
public void outbound(final IdempotencyKey idempotencyKey, final OutboundCommand command) {
    // 멱등성 기록 (IdempotencyRecord) — 이미 성공한 키면 내용만 확인하고 다시 반영하지 않는다
    final IdempotencyRecord request = IdempotencyRecord.of(idempotencyKey, OUTBOUND, command.productCode(), command.quantity(), command.requesterId());
    final Optional<IdempotencyRecord> processed = idempotencyStore.saveOrGetProcessed(request);
    if (processed.isPresent()) {
        processed.get().verifySameRequest(request);
        return;
    }
    // 상품 (Product) ... 이후는 기존과 같다
}
```
`saveOrGetProcessed`의 구현 (`IdempotencyStoreAdapter`)
1. 키 `INSERT ... ON CONFLICT DO NOTHING`. 같은 키를 다른 트랜잭션이 넣는 중이면 그 트랜잭션이 끝날 때까지 기다린다
2. 1행이면 처음 보는 키 → 빈 값. 서비스는 기존 입고, 출고 흐름을 그대로 진행한다. 같은 트랜잭션이라 실패하면 키도 함께 롤백된다
3. 0행이면 이미 성공한 키 → 저장된 기록을 읽어 돌려준다. 서비스는 내용을 비교해 같으면 재고를 건드리지 않고 끝(200), 다르면 422

- 행 수로 가르고 다시 읽는 일은 어댑터 안에 둔다. JPA에는 "없으면 넣고 있으면 그대로" 저장이 없어서(`persist`는 같은 키면 예외로 트랜잭션이 깨지고, `save`는 SELECT 후 INSERT라 동시에 들어온 같은 키가 둘 다 "없음"을 본다) native `ON CONFLICT`를 쓰는데, 이 사정은 저장 방식의 문제라 서비스가 알 필요가 없다. 서비스는 "처리한 적 있는 키인가"만 묻는다.
- 0행인데 기록이 없으면 500(`IllegalStateException`)이다. READ COMMITTED에서 충돌한 행은 커밋된 행이라 다시 읽으면 반드시 보인다. 안 보이면 앱을 거치지 않은 데이터 손상이다.
- **READ COMMITTED 전제**: "0행이면 다시 읽어서 보인다"는 READ COMMITTED에서만 성립한다. REPEATABLE READ 이상이면 `ON CONFLICT`에서 직렬화 오류가 나거나 다시 읽어도 비어 500이 된다. 아키텍처 규칙 6장대로 격리 수준을 바꾸지 않고, `IdempotencyStoreAdapter`에 이 전제를 주석으로 남긴다.
- 키를 상품, 재고보다 **먼저** 넣는다. 재전송은 재고 행 잠금까지 가지 않아서, 인기 상품의 잠금 대기 줄을 늘리지 않는다.
- 잠그는 순서가 항상 키 → 재고 하나라서, 같은 키끼리나 같은 상품끼리 서로 상대를 기다리는 데드락이 생기지 않는다.

**같은 키가 서로 다른 Pod에 동시에 올 때** (재고 5, A와 B가 같은 키로 3 출고)

| 시점 | Pod A | Pod B |
|---|---|---|
| t1 | 키 INSERT → 1행 (커밋 전) | |
| t2 | | 키 INSERT → A의 커밋을 기다림 |
| t3 | 재고 잠금, 5 → 2, 원장, **커밋** | |
| t4 | | 기다림이 풀리고 0행 → 기록을 읽어 같은 내용 확인 → 200, 재고 그대로 |

결과는 재고 2, 원장 1건, 두 응답 모두 200이다. A가 재고 부족 등으로 롤백했다면 t4에서 B의 INSERT가 1행이 되고 B가 처음부터 처리한다.

- 기다리는 동안 B는 DB 커넥션 하나를 쥐고 있다. 대기 상한은 이미 있는 `lock_timeout = 3s`(#12)가 유니크 인덱스 대기에도 걸려서 503으로 끊는다. 클라이언트가 같은 키로 다시 보내면 그때는 200을 받는다.
- 알고 받아들이는 비용: 앞 요청이 인기 상품 재고 잠금 줄에 오래 서 있는 동안 클라이언트가 같은 키로 짧은 간격으로 재시도하면, 재시도마다 커넥션 하나를 최대 3초씩 쥔다. 같은 키 폭주가 커넥션 풀을 바닥낼 수 있다. 지금은 받아들이고, 실제로 측정되면 키 INSERT에만 `SET LOCAL lock_timeout`을 짧게 주거나 IETF 초안처럼 즉시 409를 주는 것이 다음 단계다.

**왜 별도 테이블인가** (대안: 원장 `stock_transaction`에 `idempotency_key` 컬럼과 UNIQUE를 추가하고, 트랜잭션 맨 앞에서 `pg_advisory_xact_lock(hashtext(key))`로 같은 키끼리 줄을 세운 뒤 원장을 키로 조회)

대안은 테이블이 하나 적고, 요청 내용(구분, 상품, 수량, 요청자)을 원장과 별도 테이블에 두 번 저장하지 않는다. 원장은 원래 지우지 않으니 보관 기간도 저절로 같아진다.

그래도 별도 테이블을 고른 이유: 키는 재고를 바꾸기 **전에** 확인해야 하는데, 원장 행은 재고를 바꾼 **뒤에야** 생긴다. 그래서 원장에 키를 두면 앞에서 같은 키끼리 줄을 세울 장치(advisory lock)를 따로 둬야 하고, 잠금(advisory lock)과 중복 판정(원장 UNIQUE)이 서로 다른 곳에 나뉜다. 별도 테이블은 맨 앞의 키 INSERT 하나가 줄 세우기와 중복 판정을 함께 맡는다.

- 겹쳐 보이는 컬럼은 역할이 다르다. 멱등성 기록은 "요청이 무엇이었나"(재전송 판별용 지문)이고, 원장은 "재고가 어떻게 바뀌었나"(변경 전후)다. 지금은 응답이 비어 있어 내용이 겹쳐 보일 뿐이다.
- 키 수는 원장보다 많아지지 않는다. 키와 원장 행이 같은 트랜잭션에서 함께 커밋되거나 함께 롤백되므로, 키 수는 이 기능 이후의 원장 행 수와 같다. 키가 원장보다 많이 쌓이는 것은 실패한 요청의 키까지 저장할 때뿐이다(아래 "실패한 요청의 키").
- 대안이 나은 점도 있다. 응답에 데이터를 담게 되면(예: 출고 응답에 출고 후 재고) 대안은 원장 행에서 첫 응답을 그대로 재현할 수 있다. 별도 테이블은 응답을 저장하거나 원장 id를 연결하는 컬럼이 필요하다. 현재 재고로 응답을 다시 만들면 첫 응답과 달라지기 때문이다. 응답에 데이터를 담기로 할 때가 다시 검토할 시점이다.

**왜 키를 맨 앞에서 확인하나** (대안: 재고 행 잠금을 먼저 잡고, 잠근 뒤 JPA로 키를 조회해 없으면 `persist`)
- 대안은 같은 키 요청끼리의 순서를 이미 있는 재고 행 잠금에 맡긴다. 같은 키 요청은 같은 상품이라 잠금이 같다. native INSERT와 행 수 분기 없이 "잠금 → 처리한 적 있나 조회 → 없으면 기록하고 변경"으로 JPA답게 읽힌다.
- 하지만 재전송이 재고 잠금 줄에 선다. 인기 상품에 정상 요청 10건이 줄 서 있을 때 재전송 5건이 오면, 대안에서는 재전송도 그 줄 끝에 서서 정상 요청의 대기를 늘린다. 이 명세에서는 이미 처리된 키의 재전송은 키 INSERT가 바로 0행으로 끝나 잠금 줄에 들어가지 않는다.
- 한계: **처리 중인** 키의 재전송은 기다린다. 키 INSERT로 잡은 잠금은 그 블록이 끝날 때가 아니라 원래 요청의 트랜잭션이 커밋, 롤백될 때 풀리기 때문이다. 원래 요청이 재고 잠금에서 기다리는 중이면 그 시간까지 함께 기다린다. 원래 요청이 성공할지 실패할지 알아야 200으로 끝낼지 다시 처리할지 정할 수 있어서 필요한 대기이고, 상한은 `lock_timeout` 3초(넘으면 503)다. 기다리지 않게 하려면 위 "같은 키 폭주" 비용에 적은 다음 단계(키 INSERT에만 짧은 대기 시간, 넘으면 즉시 409)를 쓴다.
- 멱등성은 이미 처리된 요청을 업무 로직(상품 조회, 재고 잠금)에 들이지 않고 앞에서 끝내는 것이 목적이다. 대안은 이 목적과 반대 방향이다.
- 대안에서는 같은 키를 서로 다른 상품에 동시에 보내는 잘못된 사용이 서로 다른 잠금을 잡아 둘 다 "기록 없음"을 보고, 늦게 커밋하는 쪽이 PK 위반으로 500이 된다.

**왜 Redis가 아니라 PostgreSQL인가**
- 키와 재고가 같은 DB에 있어야 한 트랜잭션으로 묶인다. Redis에 두면 "키는 남았는데 재고 변경은 롤백됨", "처리 중 표시를 걸고 Pod가 죽어 TTL까지 막힘"을 직접 처리해야 한다. Redis 복제는 비동기라 장애 조치 중에 키가 사라져 중복이 반영될 수도 있어서, 어차피 DB 유니크 제약을 최종 방어선으로 남겨야 한다.
- Redis는 프로젝트에서 합의되지 않은 인프라다(아키텍처 규칙 6장). 키 저장 때문에 새 인프라를 들일 만한 측정된 문제가 아직 없다.
- Redis를 다시 검토할 신호: 처리 중에 외부 API를 부르거나 DB가 나뉘어 키와 변경을 한 트랜잭션에 묶을 수 없게 될 때, 또는 같은 키 재시도 폭주가 DB 커넥션을 실제로 잡아먹는 것이 측정될 때. 그때도 Redis는 앞에서 거르는 필터이고 PostgreSQL 제약이 기준이다.
- Pod 메모리는 쓸 수 없다. 재전송이 다른 Pod로 가면 막지 못한다.

**보관 기간: 영구 보관**
- 키가 필요한 기간은 재전송이 올 수 있는 동안이다(더블 클릭은 1초, 타임아웃 재시도는 수 분, 오프라인 큐는 길면 하루). 기능만 보면 영구 보관이 꼭 필요하지는 않다.
- 기간을 두고 지우려면 정리 작업이 필요하다. `@Scheduled`로 만들면 모든 Pod에서 함께 돌아서, 한 대만 돌게 할 장치(k8s CronJob, DB 락을 거는 스케줄러)가 필요하다. 그리고 기간이 지난 뒤 늦게 온 재전송은 다시 반영된다(예: 24시간 보관이면 25시간 뒤 재전송은 재고를 한 번 더 바꾼다).
- 영구 보관은 이 둘이 없다. 대신 재고 변동 1건마다 1행(100바이트 안팎)씩 원장과 같은 속도로 커진다. 하루 1만 건이면 1년에 수백 MB 수준이라 지금 규모에서는 작다.
- 커졌을 때의 경로
  - 클라이언트에 시간순 UUID(UUIDv7)를 권장한다. 무작위 UUID는 인덱스 아무 곳에나 끼어 들어가 페이지 분할이 잦은데, 시간순이면 인덱스 끝에만 쌓인다. 가장 싼 개선이다.
  - `created_at` 기준 월별 파티션으로 바꾸고 오래된 파티션을 통째로 버린다. 행 단위 DELETE보다 훨씬 싸다. 다만 파티션 테이블의 PK에는 파티션 키(`created_at`)가 들어가야 해서 키 하나만으로는 유일성을 보장할 수 없게 된다. 그때는 보관 기간을 정하는 것과 함께 설계한다. 지금은 하지 않는다.

**실패한 요청의 키: 남기지 않는다** (대안: 실패 결과도 저장해서 같은 실패를 재현)
- 예: 재고 0인 상품에 키 `K1`로 3 출고 → 409. 그 뒤 다른 작업자가 10 입고. 클라이언트가 첫 응답을 못 받았다고 보고 `K1`로 다시 보냄.
  - 남기지 않음(이 명세): 다시 처리해서 200, 재고 10 → 7.
  - 실패도 저장: 지금 재고가 10인데도 409를 다시 돌려준다. 실제로 출고하려면 새 키 `K2`로 보내야 한다.
- 두 방식 모두 재고는 많아야 한 번 바뀐다. 첫 요청은 아무것도 바꾸지 않았기 때문이다. 이슈의 목적(재고에 한 번만 반영)은 어느 쪽이든 지켜진다.
- 실패를 저장하려면 롤백되는 트랜잭션과 따로 실패 결과를 쓰는 경로(별도 트랜잭션)가 하나 더 필요하고, 그 쓰기마저 실패할 때의 동작도 정해야 한다. 실패는 상태를 바꾸지 않으니 다시 처리해도 안전하고, 추가 코드 없이 트랜잭션 롤백만으로 된다.
- 영구 보관과 함께 쓰면 실패 저장은 특히 나쁘다. 409를 받은 키는 1년 뒤에도 409다. 실패 행이 쌓여 키 수가 원장 행 수를 넘게 되는 것도 이 방식뿐이다.
- Stripe는 첫 응답을 실패까지 저장하지만, 카드사 호출처럼 트랜잭션 밖 부작용이 일부 실행됐을 수 있어서다. 여기는 모든 변경이 트랜잭션 하나라 롤백이 "아무 일도 없었음"을 보장한다. Stripe도 실행이 시작되지 않은 실패(검증 실패, 동시 요청 충돌)는 저장하지 않는다.
- 이 방식의 단점(포기한 요청이 뒤늦게 반영될 수 있음)은 위 "클라이언트 재시도 계약"으로 막는다.

**배포할 때**
- 새 테이블 추가는 구버전 코드와 호환된다.
- 롤링 배포 중에는 키를 모르는 구버전 Pod가 함께 돈다. 그 사이 재전송이 구버전 Pod로 가면 다시 반영될 수 있다. 배포 한 번 동안만 생기는 틈이라 받아들인다.
- 헤더가 필수가 되므로, 키를 보내지 않는 클라이언트는 배포 후 400을 받는다. 무중단으로 바꾸려면 "헤더가 있으면 확인, 없으면 그냥 처리"로 먼저 배포하고, 클라이언트가 모두 키를 보내기 시작한 뒤 필수로 바꾸는 두 단계가 정석이다. 이 과제는 아직 키를 보내지 않는 기존 클라이언트가 없어 한 번에 필수로 배포한다.

### 비즈니스 규칙
- R1. 입고, 출고 요청은 `Idempotency-Key`가 있어야 한다. 없으면 400 `BAD_REQUEST`, 공백이거나 65자 이상이면 400 `INVALID_IDEMPOTENCY_KEY`이고 재고는 그대로다.
- R2. 이미 성공한 키로 같은 내용을 다시 보내면 200(`data` = `null`)이고, 재고와 원장은 바뀌지 않는다.
- R3. 이미 성공한 키로 다른 내용(입고/출고 구분, 상품 코드, 수량, 요청자 중 하나라도 다름)을 보내면 422 `IDEMPOTENCY_KEY_REUSED`이고, 재고와 원장은 바뀌지 않는다.
- R4. 실패한 요청은 키를 남기지 않는다. 같은 키로 다시 보내면 처음 온 요청처럼 처리한다.
- R5. 같은 키 요청이 동시에 와도 재고와 원장에는 한 번만 반영되고, 나머지는 200이다.
- R6. 같은 키는 멱등성 기록에 한 행만 있을 수 있다 (DB 제약).
