# 기능 명세 — k6 부하 테스트 (#18)

### 요구사항 해석
- #17의 compose 구성(nginx 뒤에 앱 3대, PostgreSQL 하나)에 k6로 부하를 건다. 요청은 nginx로만 보내서 앱 3대에 나뉘어 들어가게 한다. 지금까지의 동시성 테스트(#15, #16)는 앱 하나에 스레드 여러 개였고, 이 이슈가 처음으로 **서버 여러 대**가 같은 DB를 쓰는 상황을 확인한다.
- 부하는 **상품 하나**에 입고와 출고를 섞어서 보낸다. 재고 행 잠금이 가장 심하게 겹치는 경우다.
- 부하 모양은 세 가지다. `load`(일정한 부하), `stress`(초당 요청을 단계적으로 올려 한계 지점 찾기), `spike`(평소 부하에서 갑자기 몰렸다가 돌아오기). 물류는 출고 마감 직전, 프로모션 시작처럼 요청이 순간적으로 몰리는 때가 있어서, 일정한 부하만으로는 그때 어떻게 되는지 알 수 없다.
- 일부 요청은 같은 멱등성 키로 **동시에 두 번** 보낸다. nginx가 번갈아 나눠 보내므로 두 요청은 대개 서로 다른 앱에 들어간다.
- 끝난 뒤 DB를 직접 조회해 정합성을 확인한다: 재고가 음수가 아님, 현재 재고 = 원장 합계, 같은 키가 두 번 반영되지 않음.
- `./load-test/run.sh [load|stress|spike]` 하나로 DB 초기화, 구성 기동, 부하, 정합성 확인까지 한다. 정합성이 하나라도 깨지면 0이 아닌 코드로 끝난다.
- 결과(처리량, 응답 시간, 상태 코드별 건수, 정합성 확인 결과, 실행 환경)는 `docs/load-test-result.md`에 남긴다.
- 기능 코드는 바꾸지 않는다.

### 설계

**파일**

| 파일 | 내용 |
|---|---|
| `load-test/inventory-mixed.js` | k6 스크립트 (부하 시나리오, 클라이언트 쪽 집계) |
| `load-test/consistency.sql` | 정합성 확인 SQL. 위반 건수를 한 줄씩 출력한다 |
| `load-test/run.sh` | 전체 실행 (아래 "흐름") |
| `infra/compose.yaml` | `app`에 healthcheck 추가, `k6` 서비스 추가 (`profiles: [load]`라 평소 `up`에는 뜨지 않는다) |
| `infra/nginx.conf` | 워커 연결 수 상한을 올리고, 앱으로 가는 연결을 재사용(keepalive)한다 (아래 "nginx 설정을 바꾸는 이유") |
| `docs/load-test-result.md` | 결과 기록 |
| `README.md` | 실행 섹션에 부하 테스트 명령 한 줄 |

**흐름** (`load-test/run.sh`)
1. `docker compose down -v` 후 `docker compose up -d --build --wait`: 빈 DB에서 시작하고, 앱 3대가 healthy가 될 때까지 기다린다.
2. `docker compose run --rm k6 run -e SCENARIO={시나리오} ...`: 부하를 건다. 인자가 없으면 `load`다. k6가 끝나면 요약 수치와 "성공한 키 수"를 파일로 남긴다.
3. `docker compose exec postgres psql -f consistency.sql`: 정합성 위반 건수를 확인한다.
4. k6가 센 성공 키 수와 원장 행 수를 비교한다.
5. 3, 4 중 하나라도 어긋나면 exit 1.

**k6를 컨테이너로 돌리는 이유** (대안: 호스트에 설치한 k6로 `localhost:8080`에 보냄)
- 다시 돌리는 사람이 k6를 설치하지 않아도 되고, k6 버전이 이미지 태그로 고정된다. 버전이 다르면 같은 스크립트도 수치가 달라질 수 있다.
- compose 네트워크 안에서 `nginx`로 바로 보내므로, Docker Desktop의 포트 포워딩을 거치지 않는다. 포트 포워딩은 맥에서 요청당 지연을 눈에 띄게 늘려 앱이 아니라 포워딩 속도를 재게 된다.
- 단점: k6가 앱, DB와 같은 Docker 자원(CPU)을 나눠 쓴다. 호스트 k6도 같은 머신이라 차이는 작고, 결과 문서에 환경과 함께 적는다.

**앱 healthcheck 추가 이유**
- 지금 compose에는 앱 healthcheck가 없어서, `up`이 끝나도 앱이 아직 기동 중일 수 있다. 그때 부하를 시작하면 첫 요청들이 502가 되어 결과에 섞인다.
- `wget -qO- localhost:8081/actuator/health/readiness`(관리 포트)로 확인하고(alpine에 wget이 있다), `up --wait`가 healthy를 기다린다. nginx의 `depends_on`도 `service_healthy`로 바꿔 nginx가 준비된 앱만 보고 뜨게 한다.

**공통 요청** (`inventory-mixed.js`) — 세 시나리오가 같은 요청을 보내고 부하 모양만 다르다

| 항목 | 값 | 이유 |
|---|---|---|
| 상품 | `LOAD-TEST-01` 하나 | 재고 행 잠금이 모두 한 행에 몰리는 가장 나쁜 경우 |
| 시작 재고 | 50 (setup에서 입고) | 낮게 두어 출고가 재고 부족(409)에 자주 걸리게 한다. 음수가 되지 않음을 확인하려면 재고가 0 근처를 오가야 한다 |
| 요청 | 반은 입고, 반은 출고, 수량 1 ~ 5 무작위 | 입고와 출고가 비슷해 재고가 0 근처를 오르내린다 |
| 같은 키 재전송 | 요청의 20%는 같은 키로 두 번을 동시에 (`http.batch`) | 더블 클릭, 타임아웃 재시도가 서로 다른 앱에 동시에 들어가는 경우 |

- 예: 재고 2에서 출고 3은 409이고 재고 2 그대로다. 입고 4와 출고 3이 동시에 오면 어느 쪽이 먼저든 둘 다 반영되거나(입고 먼저) 출고만 409다(출고 먼저). 어느 경우든 재고는 음수가 되지 않고 원장 합계와 같아야 한다.
- 기대 상태 코드는 200, 409(재고 부족)다. 503(잠금 대기 3초 초과), 500(커넥션 풀 대기 3초 초과 등), 502, 504와 그 밖의 코드는 실패로 세고 건수를 결과에 적는다. 503은 키를 남기지 않고 롤백되므로 정합성을 깨지 않는다(#15 R4).
**부하 모양**

| 시나리오 | k6 실행기 | 모양 | 알 수 있는 것 |
|---|---|---|---|
| `load` | `constant-vus` | VU 50명, 60초 | 평소 수준의 부하에서 정합성과 응답 시간. 앱 3대의 커넥션 풀 합(30)보다 많아 풀 대기와 잠금 대기가 함께 생긴다 |
| `stress` | `ramping-arrival-rate` | 초당 200, 400, 600, 800, 1,000, 1,200회. 단계마다 5초 동안 올리고 20초 유지 (총 150초) | 상품 하나의 재고 행 잠금이 감당하는 처리량 한계. 한계를 넘으면 어떤 오류(503, 500, 502)가 나는지, 그때도 정합성이 맞는지 |
| `spike` | `ramping-arrival-rate` | 초당 200회 30초 → 5초 만에 1,500회 → 20초 유지 → 5초 만에 200회 → 10초(몰린 직후) + 30초 유지 | 갑자기 몰릴 때 버티는지, 몰림이 끝난 뒤 응답 시간이 몰리기 전 수준으로 돌아오는지. 몰린 직후 10초를 따로 떼어 회복에 걸리는 시간을 본다 |

- 회 = 반복(iteration) 한 번. 20%는 같은 키 두 요청이라 실제 요청 수는 약 1.2배다.
- stress, spike는 **도착률 기반**(`arrival-rate`)이다. VU 수를 정하는 방식(`constant-vus`)은 응답이 느려지면 VU가 다음 요청을 늦게 보내 부하가 저절로 줄어든다. 실제 몰림은 서버가 느려져도 요청이 줄지 않으므로, 초당 몇 회를 보낼지 정하고 그만큼 보낸다. 응답을 기다리는 VU가 모자라면 k6가 VU를 더 만들고(최대 2,000), 그래도 모자라면 그 반복을 건너뛰고 `dropped_iterations`로 센다. 건너뛴 수가 많다는 것도 시스템이 못 따라간다는 신호라 결과에 적는다.
- 단계(`stress`의 초당 200 ~ 1,200회, `spike`의 몰리기 전, 몰림, 몰린 뒤)마다 태그를 붙여 처리량, p95, 상태 코드별 건수를 단계별로 따로 집계한다. 단계 사이를 올리는 5초 구간은 합계에만 들어간다.
- 단계 값은 `load`에서 측정한 처리량(초당 약 700회)을 기준으로, 그 아래부터 위까지 걸치게 잡았다.

**nginx 설정을 바꾸는 이유**
- 지금 nginx는 `events {}` 기본값이라 워커 1개가 동시 연결 512개까지만 받는다. 요청 하나가 클라이언트 쪽과 앱 쪽 연결 두 개를 쓰므로 동시 요청 약 250개에서 nginx가 먼저 막힌다. 그러면 stress, spike에서 앱이 아니라 nginx의 한계를 재게 된다. 워커를 CPU 수만큼(`worker_processes auto`), 워커당 연결을 4,096개로 올린다.
- 앱으로 가는 연결을 요청마다 새로 열면, 초당 1,000회 이상에서 연결을 열고 닫는 비용이 응답 시간에 섞이고 nginx 컨테이너의 임시 포트가 바닥날 수 있다. `keepalive 64`로 앱 연결을 재사용한다. 운영의 Ingress도 기본으로 앱 연결을 재사용하므로 운영과 더 비슷해진다.
- 둘 다 nginx 설정만 바꾸고, 앱의 동작은 바꾸지 않는다.

- 응답 시간 목표(threshold)는 두지 않는다. 기준으로 삼을 요구 수치가 없고, 수치는 실행 머신에 따라 달라진다. 이 테스트의 합격 기준은 정합성이고, 수치는 기록한다.

**클라이언트 쪽 집계** — "같은 키가 두 번 반영되지 않음"을 확인하는 기준
- 키마다 "200을 한 번이라도 받았는가"를 센다(`applied_keys` 카운터). 같은 키 두 요청이 둘 다 200이어도 1로 센다.
- 반영된 키 하나 = 원장 한 행이어야 한다. 그래서 **`applied_keys` = 원장 행 수**(setup의 시작 입고 1건 포함)가 기대값이다. 같은 키가 두 번 반영되면 원장이 더 많아진다.
- k6의 `handleSummary`로 `applied_keys`를 파일에 써서 `run.sh`가 원장 행 수와 비교한다.

**정합성 SQL** (`consistency.sql`) — 모두 0이어야 한다

| 확인 | 쿼리 요지 |
|---|---|
| 음수 재고 | `inventory`에서 `quantity < 0`인 행 수 |
| 재고 ≠ 원장 합계 | 상품별 `inventory.quantity`와 `SUM(입고) - SUM(출고)`가 다른 상품 수 |
| 멱등성 기록 ≠ 원장 | `idempotency_record` 행 수와 `stock_transaction` 행 수의 차이. 둘은 같은 트랜잭션에서 함께 커밋된다 |

- CHECK 제약(`quantity >= 0`)이 이미 음수를 막지만, 제약을 지우는 실수가 있어도 이 확인이 잡도록 따로 센다.
- 잠금 없이 두 요청이 같은 재고를 읽고 각자 덮어쓰면(잃어버린 갱신) "재고 ≠ 원장 합계"에서 드러난다. 예: 재고 5에 입고 3 두 건이 둘 다 5를 읽고 8을 쓰면, 재고는 8인데 원장 합계는 11이다.

**결과 문서** (`docs/load-test-result.md`)
- 실행 환경: 머신(CPU, 메모리), Docker 자원 할당, 커밋 SHA, k6 버전
- 구성: nginx → 앱 3대(풀 10씩), PostgreSQL 16 하나
- 시나리오별로 아래를 적는다. stress, spike는 단계별 표를 함께 둔다
- 수치: 총 요청 수, 처리량(req/s), 응답 시간 p50, p95, p99, max, 상태 코드별 건수(200, 409, 500, 502, 503, 504, 그 밖), 건너뛴 반복 수(stress, spike)
- 앱별 요청 분포: nginx 로그의 upstream 주소별 건수 (요청이 실제로 3대에 나뉘었다는 근거)
- 정합성: 위 세 가지 확인 결과와 `applied_keys` = 원장 행 수
- 해석: 상품 하나에 몰리면 앱을 늘려도 재고 행 잠금 하나를 차례로 지나가서 처리량이 늘지 않는다는 점 등, 측정에서 보인 것만 적는다

### 비즈니스 규칙
- R1. 명령 하나(`./load-test/run.sh`)로 빈 DB에서 구성 기동, 부하, 정합성 확인까지 다시 돌릴 수 있다.
- R2. 부하는 nginx를 거쳐 앱 3대에 나뉘어 들어간다.
- R3. 부하가 끝난 뒤 재고는 음수가 아니고, 현재 재고 = 원장 합계다.
- R4. 같은 키는 한 번만 반영된다: 성공한 키 수 = 원장 행 수 = 멱등성 기록 행 수.
- R5. 정합성이 하나라도 깨지면 `run.sh`는 0이 아닌 코드로 끝난다.
- R6. 결과가 `docs/load-test-result.md`에 남는다.
- R7. `stress`, `spike`도 같은 명령에 인자만 바꿔 돌릴 수 있고, 한계를 넘어 오류가 나도 정합성은 맞는다.

### 검증 방법
k6 스크립트와 셸 스크립트라 테스트 코드 대신 실제 실행으로 확인한다. 명령은 레포 루트에서 실행한다.

| 대상 규칙 | 실행 | 기대 결과 |
|---|---|---|
| R1, R3, R4 | `./load-test/run.sh; echo $?` | k6 요약 출력, 정합성 위반 0 세 줄, `applied_keys` = 원장 행 수, exit 0 |
| R1 | 한 번 더 `./load-test/run.sh` | 앞 실행의 데이터 없이 같은 결과 (시작할 때 DB를 비운다) |
| R2 | 실행 후 `docker compose -f infra/compose.yaml logs nginx \| grep -o 'upstream=[^ ]*' \| sort \| uniq -c` | 서로 다른 upstream 3개에 비슷하게 나뉨 |
| R5 | 실행 후 `psql`로 재고를 1 바꾸고(`UPDATE inventory SET quantity = quantity + 1`) 정합성 단계만 다시 실행 | "재고 ≠ 원장 합계" 1, exit 1 |
| R6 | `docs/load-test-result.md` | 위 "결과 문서"의 항목이 실제 실행 수치로 채워져 있음 |
| R7 | `./load-test/run.sh stress; echo $?`, `./load-test/run.sh spike; echo $?` | 단계별 수치 출력, 정합성 위반 0, `applied_keys` = 원장 행 수, exit 0 |
