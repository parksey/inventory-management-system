# 기능 명세 — 입출고 혼합 동시성 검증 (#16)

### 요구사항 해석
- 지금까지의 동시성 테스트는 입고만, 출고만 동시에 보냈다. 이 이슈는 **같은 상품에 입고와 출고가 섞여 동시에** 와도 재고가 정확한지 테스트 코드로 확인한다.
- 이슈의 나머지 시나리오는 이미 테스트가 있거나 다른 곳에서 확인한다.

| 이슈의 시나리오 | 처리 |
|---|---|
| 입고와 출고가 섞인 동시 요청 | 이 이슈에서 추가 (TC-16-01) |
| 처음 보는 상품의 동시 입고 | 이미 있음: TC-12-14(20건 동시 입고에 상품 1건), TC-12-17(등록 중인 상품의 커밋을 기다림) |
| 같은 키 동시 요청 | 이미 있음: TC-15-13, TC-15-14(같은 키 20건 동시 입고, 출고에 한 번만 반영) |
| 서버 여러 대가 같은 DB를 쓰는 상황 | k6 부하 테스트(#18)에서 앱 컨테이너 여러 개로 확인 |

- 테스트는 `./gradlew build`에 포함되어 CI(#6)에서 매번 돈다.
- 기능 코드는 바꾸지 않는다.

### 설계

**왜 서버 하나로 확인하나** (대안: 테스트 안에서 같은 DB를 보는 앱 인스턴스 두 개를 띄움)
- 정합성은 앱이 아니라 DB(재고 행 잠금, 제약)가 보장하고, 앱 서버는 상태를 갖지 않는다. DB 입장에서 서버 두 대는 커넥션이 여러 개인 것과 같아서, 서버 하나에 동시 요청을 여러 스레드로 보내면 같은 경합이 재현된다.
- 같은 JVM에 인스턴스 두 개를 띄워도 추가로 잡는 것은 빈 안에 상태를 둔 경우 정도다. 다중 서버에서 가장 위험한 JVM 전역 상태(`static`, 클래스 단위 `synchronized`)는 같은 JVM이라 못 잡는다.
- 진짜 다중 서버는 앱 컨테이너(#17)를 여러 개 띄우는 k6 부하 테스트(#18)에서 확인한다.

**테스트** — 기존 `InventoryConcurrencyTest`에 추가한다. 같은 클래스의 `concurrently`(스레드를 모두 준비시킨 뒤 한 번에 출발)를 그대로 쓴다.
- 재고 100에서 출고 30건, 입고 40건(각 수량 1)을 동시에 보낸다.
- 재고가 충분해 출고가 실패할 일이 없으므로 결과가 하나로 정해진다: 모두 200, 재고 110.

### 비즈니스 규칙
- R1. 같은 상품에 입고와 출고가 섞여 동시에 와도, 재고는 시작 재고 - 성공한 출고 합 + 성공한 입고 합이고 원장 합계와 같다.

### 예외 케이스
- 없음 (재고가 충분해 출고 실패가 생기지 않는 조건으로 구성한다. 재고 부족이 섞인 동시 출고는 TC-13-12가 확인한다)
