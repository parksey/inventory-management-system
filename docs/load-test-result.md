# 부하 테스트 결과 (k6)

앱 여러 대가 같은 DB를 쓰는 구성에서 상품 하나에 입고, 출고를 동시에 몰아 보내고, 끝난 뒤 재고 정합성을 확인한 결과다. 시나리오와 확인 기준은 [기능 명세](specs/18-k6-load-test.md)에 있다.

다시 돌리기 (레포 루트에서):
```bash
./load-test/run.sh            # load: VU 50명, 60초
./load-test/run.sh stress     # 초당 200 ~ 1,200회로 단계적으로 올림
./load-test/run.sh spike      # 초당 200회 → 1,500회로 몰렸다가 돌아옴
```
매번 빈 DB에서 구성을 띄우고, 부하가 끝나면 정합성을 확인한다. 정합성이 깨지면 exit 1이다.

## 환경
| 항목 | 값 |
|---|---|
| 머신 | Apple M4 Pro (12코어), 메모리 48GB, macOS 15.3.1 |
| Docker | Docker Desktop, 할당 CPU 12, 메모리 16GB |
| 구성 | k6 → nginx → 앱 3대 (커넥션 풀 10씩, 풀 대기 3초) → PostgreSQL 16 하나 (`max_connections` 100, 잠금 대기 3초). 모두 같은 머신의 컨테이너 |
| 버전 | 커밋 `2543147`(dev, 로깅과 모니터링 포함) + 이 브랜치의 부하 테스트 파일, k6 1.6.1 |
| 실행일 | 2026-10-16 |

## 공통 요청
| 항목 | 값 |
|---|---|
| 상품 | `LOAD-TEST-01` 하나 (모든 쓰기가 재고 행 하나의 잠금을 두고 경합) |
| 시작 재고 | 50 |
| 요청 | 입고, 출고 반반, 수량 1 ~ 5 무작위 |
| 같은 키 재전송 | 반복의 20%는 같은 멱등성 키로 두 요청을 동시에 보냄. 그래서 요청 수는 반복 수의 약 1.2배다 |

## 요약
| 시나리오 | 요청 | 처리량 | p95 | 200 | 409 | 500 | 503 | 건너뛴 반복 | 정합성 |
|---|---|---|---|---|---|---|---|---|---|
| load | 50,874 | 844.7 req/s | 172.4ms | 50,778 | 96 | 0 | 0 | 0 | 통과 |
| stress | 107,437 | 703.9 req/s | 2,737.0ms | 107,434 | 0 | 3 | 0 | 13,014 | 통과 |
| spike | 45,213 | 451.3 req/s | 3,002.5ms | 44,817 | 396 | 0 | 0 | 14,896 | 통과 |

- 502, 504와 그 밖의 상태 코드는 세 시나리오 모두 0건이다.
- stress, spike의 처리량과 p95는 전체 구간을 합친 값이라 단계마다 크게 다르다. 아래 단계별 표를 본다.
- "건너뛴 반복"은 k6가 정한 도착률을 맞추려 했지만 응답을 기다리는 VU 2,000명이 모두 차서 보내지 못한 반복이다. 시스템이 못 따라간다는 신호다.

## load — VU 50명, 60초
| 항목 | 값 |
|---|---|
| 응답 시간 | avg 68.7ms, p50 54.2ms, p95 172.4ms, p99 293.8ms, max 944.7ms |
| 앱별 요청 수 (nginx upstream) | 16,959 / 16,953 / 16,962 |
| 같은 키 재전송 | 200 중 8,446건 (200 건수 - 반영된 키 수). 재고를 다시 바꾸지 않았다 |
| 최종 재고 | 227 = 입고 합 63,512 - 출고 합 63,285 |

- VU 50명이 응답을 받자마자 다음 요청을 보내므로, 동시 요청은 늘 50 ~ 60개다. 앱 3대의 커넥션 풀 합(30)보다 많아서 요청이 풀 앞에서 잠깐씩 기다리고, 그래서 p50이 50ms대다.

## stress — 초당 200 ~ 1,200회
| 단계 (목표 반복/s) | 실제 처리량 | p95 | 200 | 409 | 500 |
|---|---|---|---|---|---|
| 200 | 240 req/s | 6ms | 4,800 | 0 | 0 |
| 400 | 483 req/s | 4ms | 9,662 | 0 | 0 |
| 600 | 722 req/s | 3ms | 14,437 | 0 | 0 |
| 800 | 951 req/s | 366ms | 19,028 | 0 | 0 |
| 1,000 | 1,026 req/s | 2,860ms | 20,519 | 0 | 2 |
| 1,200 | 923 req/s | 3,218ms | 18,452 | 0 | 1 |

- **한계는 약 950 ~ 1,000 req/s다.** 600회까지는 p95가 3 ~ 6ms다. 800회(951 req/s)에서 처리는 따라가지만 p95가 366ms로 늘어 줄이 생기기 시작하고, 1,000회에서 2.9초로 뛰면서 반복을 건너뛰기 시작한다.
- 한계를 넘으면 처리량이 더 늘지 않고 오히려 줄었다(1,200회에서 923 req/s). 늘어난 요청은 처리되지 못하고 커넥션 풀 앞에 줄을 선다.
- 이때의 실패는 500 3건이다. 앱 로그를 보면 원인은 모두 커넥션 풀 대기 3초 초과다(`Connection is not available, request timed out after 3000ms (total=10, active=10, idle=0, waiting=189)`).
- 정합성: 음수 재고 0, 재고 ≠ 원장 합계 0, 반영된 키 89,485 = 원장 89,485행.

## spike — 초당 200회 → 1,500회 → 200회
| 단계 | 길이 | 실제 처리량 | p95 | 200 | 409 | 500 |
|---|---|---|---|---|---|---|
| 몰리기 전 (200회) | 30초 | 241 req/s | 7ms | 7,179 | 60 | 0 |
| 몰림 (1,500회) | 20초 | 1,009 req/s | 3,177ms | 19,960 | 227 | 0 |
| 몰린 직후 (200회) | 10초 | 237 req/s | 1,780ms | 2,314 | 56 | 0 |
| 그 뒤 (200회) | 30초 | 243 req/s | 4ms | 7,277 | 0 | 0 |

- 몰리는 동안 처리량은 stress에서 본 한계(약 1,000 req/s)에 머물고, 넘친 요청은 응답이 3초 가까이 걸리거나 건너뛰었다. 이번 실행에서는 커넥션 풀 대기가 3초를 넘은 요청이 없어 500은 0건이었다. 한계 근처라 실행마다 몇 건씩 날 수 있다(stress에서는 3건).
- **몰림이 끝나고 10초 안에 회복했다.** 직후 10초는 밀린 요청이 빠지느라 p95가 1.8초였고, 그 뒤 30초는 몰리기 전 수준(4ms)으로 돌아왔다. 앱이 죽거나 재시작되지 않았다.
- 정합성: 음수 재고 0, 재고 ≠ 원장 합계 0, 반영된 키 37,268 = 원장 37,268행.

## 정합성 확인 방법
| 확인 | 기대 |
|---|---|
| 음수 재고 | 0행 |
| 재고 ≠ 원장 합계 | 0행 |
| 멱등성 기록 행 수 ≠ 원장 행 수 | 차이 0 |
| 반영된 키 수 (k6 집계) = 원장 행 수 | 같음 |

- "반영된 키"는 k6가 키마다 200을 한 번이라도 받았으면 1로 센 값이다. 같은 키 두 요청이 둘 다 200이어도 1이다. 이 수가 원장 행 수와 같으므로 같은 키가 두 번 반영된 경우는 없다.
- 세 시나리오 모두 네 가지가 기대대로였다. 한계를 넘어 500이 나고 요청을 건너뛴 stress, spike에서도 마찬가지다. 실패한 요청은 트랜잭션이 롤백되어 키도 재고 변경도 남기지 않는다.

## 해석
- **정합성은 부하 크기와 상관없이 지켜졌다.** 앱 3대에 요청이 고르게 나뉜 상태에서, 한계를 넘는 몰림에서도 재고, 원장, 멱등성 기록이 맞았다. 서버 수와 상관없이 DB의 재고 행 잠금과 멱등성 키 PK가 정합성을 지킨다.
- **상품 하나의 처리량 한계는 초당 약 1,000건이다.** 같은 상품의 쓰기는 재고 행 잠금 하나를 차례로 지나가므로, 앱을 늘려도 이 한계는 늘지 않는다. 상품이 여러 개로 나뉘면 잠금도 나뉘어 전체 처리량은 더 높을 것이지만, 이번에 측정하지는 않았다.
- **한계를 넘은 요청은 DB 잠금이 아니라 앱의 커넥션 풀 앞에서 기다린다.** 그래서 잠금 대기 초과(503)는 0건이고, 풀 대기 초과가 500으로 나갔다. 둘 다 잠시 뒤 다시 보내면 되는 일시적 과부하인데 상태 코드가 다르다. 클라이언트 재시도 계약상 5xx는 같은 키로 재시도하므로 중복 반영 위험은 없지만, 풀 대기 초과도 503과 `Retry-After`로 알려 주는 편이 맞다. 이 이슈 범위가 아니라 별도로 다룬다.
- 409가 적은 이유: 출고가 재고 부족으로 거절되면 재고가 그만큼 덜 줄어서, 입고와 출고가 반반이어도 재고가 시작값 50에서 위로 올라간다. 재고가 0 근처에 머무는 동안에만 409가 나서, 실행마다 건수가 크게 다르다(stress 0건, spike 396건).
- 수치는 앱, DB, k6가 한 머신에 있는 환경의 값이라 운영 성능으로 옮겨 읽을 수 없다. 이 결과에서 옮겨 읽을 수 있는 것은 정합성과 한계에서의 동작(오류 종류, 회복)이다.
