# 요구사항 구체화

```
기능 요구사항 ── 구체화 ──▶ Issue  Issue  Issue …  ──▶ (이슈마다 issue-workflow)
   (PM)        (PM + AI)
```

이 skill은 **PM 역할**을 돕는다. 핵심은 **하나의 큰 요구사항을 AI 세션 하나로 끝낼 수 있는 작은 이슈 여러 개로 나누는 것**이다.
- 결과물: 요구사항 이슈 1개 + 그 아래 sub-issue 여러 개. 각 이슈에는 "무엇을 할지"만 담는다.
- 나누는 기준: 크기, 선행 관계, 병렬 가능 여부 (3장)
- 하지 않는 것: 어떻게 개발할지(기능 명세서)는 `issue-workflow` skill이 이슈마다 따로 다룬다.

- 규칙 원본(사람용): `docs/conventions/workflow.md` §3.1 · §4, `docs/conventions/git.md` §3
- 이슈 템플릿: `.github/ISSUE_TEMPLATE/`
- 원본과 이 문서가 다르면 원본이 맞다.

## 지켜야 할 것
- **이슈에는 무엇을만 쓴다.** 설계, 클래스, 테이블, 구현 방법을 쓰지 않는다. 그건 기능 명세서의 일이고, 이슈에 섞이면 명세서 단계에서 다시 판단할 여지가 사라진다.
- **추측해서 채우지 않는다.** 사용자가 말하지 않은 요구사항은 만들어 넣지 않고 질문하거나 Open Questions에 남긴다.
- **등록 전에 승인을 받는다.** 이슈는 공개 산출물이고 PM의 결정이다.
- 비공개 작업 문서(`.pm-plans/`)의 경로나 내부 메모를 이슈에 넣지 않는다.

## 절차

### 1. 요구사항 정리
사용자가 준 요청을 **사용자 관점**으로 다시 쓴다: "~할 수 있어야 한다".
`.github/ISSUE_TEMPLATE/1-requirement.yml`의 섹션(배경 / 요구사항 / 성공 기준 / 제약 · 범위 밖)으로 초안을 만들어 보여준다.

### 2. 구체화
요구사항의 빈칸을 질문으로 드러낸다. 질문은 한 번에 모아서, 추천 답과 함께 던진다.

| 관점 | 질문 예 |
|---|---|
| 입력 · 범위 | 수량의 상한은? 식별자는 무엇인가? |
| 예외 상황 | 재고가 부족하면? 없는 상품이면? 같은 요청이 두 번 오면? |
| 범위 밖 | 이번에 하지 않을 것은? (부분 출고, 다중 창고 등) |
| 다른 기능과의 관계 | 입고와 공유하는 규칙은? 먼저 있어야 하는 기능은? |
| 비기능 | 동시 요청, 다중 서버, 성능 기준이 있는가? |

질문을 만들기 위해 코드를 가볍게 살펴보는 건 괜찮다 (관련 모듈, 비슷한 기능이 있는지 — 깊게 들어가지 않는다).
PM의 답으로 요구사항 초안을 갱신한다. 답이 안 나온 항목은 Open Questions로 남긴다.

### 3. 이슈 도출
구체화 결과에서 "해야 할 일"을 뽑아 이슈로 나눈다.

유형(기능 개발 `2-feature`, 기능 수정 `3-change`, 버그 수정 `4-bug`, 작업 `5-task`)과 **크기 체크** 기준은 workflow.md §3.1을 따른다.

너무 잘게 쪼개지도 않는다. 혼자서는 동작을 검증할 수 없는 조각(예: "필드 추가"만 하는 이슈)은 옆 이슈와 합친다.

**선행 관계 · 병렬** — 어떤 이슈가 먼저 끝나야 하는지, 동시에 진행해도 같은 파일을 건드리지 않는지 정한다.

### 4. PM 승인
아래 형식으로 보여주고 승인을 받는다.

```markdown
**[요구사항] 재고 출고**

| 순서 | 유형 | 제목 | 우선순위 | 선행 | 완료 조건 요약 |
|---|---|---|---|---|---|
| 1 | 기능 개발 | feat(inventory): 상품 출고 | P0 | — | 재고 감소, 부족 시 거절 |
| 2 | 작업 | test(inventory): 동시 출고 정합성 검증 | P0 | 1 | 동시 요청에도 초과 출고 없음 |
```

### 5. 등록
승인되면 요구사항 이슈부터, 그다음 선행 이슈 순서로 만든다.

```bash
# 요구사항 이슈
gh issue create --title "[요구사항] 재고 출고" --label requirement \
  --milestone "v1.0.0 MVP" --body-file "$(git rev-parse --git-dir)/req.md"

# 하위 이슈
gh issue create --title "feat(inventory): 상품 출고" --label "feat,P0" \
  --milestone "v1.0.0 MVP" --body-file "$(git rev-parse --git-dir)/issue-1.md"

# sub-issue 연결 (REST는 이슈 번호가 아니라 내부 id를 받는다)
child_id=$(gh api repos/{owner}/{repo}/issues/{하위번호} --jq .id)
gh api -X POST repos/{owner}/{repo}/issues/{요구사항번호}/sub_issues -F sub_issue_id="$child_id"

# 선행 관계 — GitHub issue dependencies (하위번호가 선행번호에 blocked by)
blocker_id=$(gh api repos/{owner}/{repo}/issues/{선행번호} --jq .id)
gh api -X POST repos/{owner}/{repo}/issues/{하위번호}/dependencies/blocked_by -F issue_id="$blocker_id"
```

- 본문은 해당 템플릿의 섹션을 그대로 따른다. 선행 관계는 본문이 아니라 위 dependencies로 건다.
- 마일스톤이 없으면 만들지 말고 사용자에게 알린다.
- 이슈 번호는 PR과 같은 번호 체계를 쓰므로 미리 정할 수 없다. 생성된 번호를 받은 뒤 그 번호로 브랜치 · 커밋 · Flyway 버전 · 테스트 케이스 ID가 정해진다.

### 6. 결과 보고
생성된 이슈 번호와 링크, 추천 착수 순서, 병렬로 진행할 수 있는 이슈를 알린다.

## 개발 중에 새 이슈가 필요할 때
`issue-workflow` 진행 중 범위 밖 작업이나 버그를 발견하면 이 skill로 돌아온다.
- 버그 · 기능 수정은 요구사항 이슈 없이 바로 이슈로 만들 수 있다. 관련 요구사항이 있으면 그 sub-issue로 연결한다.
- 현재 이슈를 나눠야 하면, 원래 이슈 본문을 줄인 범위로 수정하고 떼어낸 부분을 새 이슈로 만든 뒤 서로 링크를 남긴다.
